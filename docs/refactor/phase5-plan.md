# Phase 5 执行与验收基线：可运维化与规模化落地

**版本**: 1.0  
**日期**: 2026-02-12  
**状态**: In Progress (Execution + Acceptance Baseline)

---

## 1. 阶段目标

Phase 5 聚焦“上线后长期稳定运行”，目标是把前 4 个阶段的工程能力转化为生产运营能力：

1. 可观测：关键链路具备指标、日志、告警三位一体可定位能力。
2. 可恢复：高频故障具备自动恢复路径，复杂故障具备标准化人工处置路径。
3. 可扩展：形成容量模型与调优基线，支撑业务增长。
4. 可交付：建立灰度、回滚、复盘闭环，形成稳定发布节奏。

---

## 2. 范围与非目标

### 2.1 范围

1. 生产运维能力建设：SLO/SLI、Dashboard、告警、值班、Runbook。
2. 故障治理能力建设：自动恢复策略、故障分级、处置矩阵、演练机制。
3. 容量与性能治理：基准压测、容量评估、关键参数调优、数据归档策略。
4. 上线与持续改进：灰度发布、回滚演练、周度复盘与优化 backlog。

### 2.2 非目标

1. 不进行系统级分布式重写（例如多实例一致性方案重构）。
2. 不引入重型中间件作为本阶段前置（例如 MQ、流式平台）。
3. 不进行 UI 大规模改版（仅允许必要的运维可视化补充）。

## 3. 里程碑（M1-M4）与验收

## M1：SLO 与观测基线（第 1 周）

### 目标

1. 冻结核心 SLO/SLI 与告警分级口径。
2. 建立统一可观测基线（Metrics + Logs + Alerts）。

### 主要工作

1. 定义并评审 SLO：
   - 健康检查可用率（30d）>= 99.9%
   - 转码成功率（24h rolling）>= 98%
   - 可重试失败队列不连续增长超过 30 分钟
2. 补齐关键指标与统一标签（`status`, `category`, `reason`, `phase`）。
3. 构建面板和告警规则（P0/P1/P2），落地告警路由和抑制策略。

### 验收标准

1. 核心 SLI 在 Dashboard 可追溯到任务维度（可按 task_id 或错误类别下钻）。
2. 故障注入可触发正确级别告警，误报率可控（同类告警去重生效）。
3. 值班通知链路可达（告警到达率 100%，有回执记录）。

### 验证方式

1. 执行故障注入脚本并保留告警触发截图/日志。
2. 采集 24h 监控样本，核对 SLI 计算口径与面板一致。
3. 抽检 3 条告警，验证可回溯到具体任务与日志链路。

### 输出物

1. `docs/refactor/phase5-slo.md`（SLO 定义、计算窗口、告警阈值）。
2. `docs/runbooks/alerts-routing.md`（告警路由、抑制策略、值班流程）。

---

## M2：故障治理与自愈（第 2-3 周）

### 目标

1. 落地高频故障自动恢复策略。
2. 形成“自动处理 + 人工兜底”闭环。

### 主要工作

1. 落地自愈动作：
   - `cleanup_error` 自动重试与退避
   - Worker 卡住检测后的自动回收/节流
2. 建立故障分级与处置矩阵（自动处理/人工处理/禁止重试）。
3. 输出 Runbook（覆盖至少 10 类高频故障）。

### 验收标准

1. 预设故障（磁盘不足、权限异常、短时 I/O 抖动）可自动恢复或命中标准人工步骤。
2. 单次故障从告警到定位 <= 10 分钟。
3. 不出现“静默失败”（失败必须有状态、日志、告警至少其一）。

### 验证方式

1. 执行故障演练清单并记录 MTTD/MTTR。
2. 抽样检查近 50 条失败任务，验证错误分类与处置动作一致。
3. 按 Runbook 执行一次值班交接演练并记录偏差项。

### 输出物

1. `docs/runbooks/phase5-incident-runbook.md`
2. `docs/refactor/phase5-test-report.md`（故障演练章节）

---

## M3：容量与性能治理（第 3-4 周）

### 目标

1. 建立可复用的压测方法与容量模型。
2. 在目标负载下保持吞吐稳定、延迟可预测。

### 主要工作

1. 构建压测基线（10k 任务、混合失败、回收站负载、并发扫描）。
2. 完成数据层优化（关键索引、历史归档/清理策略）。
3. 完成参数调优（Worker 上限、调度周期、校验预算、重试退避参数）。

### 验收标准

1. 目标负载下无持续队列抖动或吞吐塌陷。
2. 扫描与转码并发时，健康检查 p95 响应稳定（阈值见 `phase5-slo.md`）。
3. 产出容量建议表（CPU/内存/磁盘/并发映射 + 推荐阈值）。

### 验证方式

1. 执行标准压测脚本并归档结果（吞吐、失败率、资源占用曲线）。
2. 对比优化前后基线，给出提升或回退结论。
3. 执行一次异常压力场景（I/O 抖动或磁盘接近阈值）并验证降级行为。

### 输出物

1. `docs/refactor/phase5-capacity-model.md`
2. `docs/refactor/phase5-test-report.md`（压测章节）

## M4：灰度上线与运营闭环（第 5 周）

### 目标

1. 建立可重复执行的灰度与回滚流程。
2. 完成上线后的复盘与持续优化机制。

### 主要工作

1. 灰度放量：`10% -> 50% -> 100%`，每阶段定义观测窗口与 Go/No-Go 条件。
2. 回滚演练：配置级回滚、版本级回滚、演练记录固化。
3. 运营机制：上线周报、故障复盘、容量趋势跟踪与 backlog 治理。

### 验收标准

1. 灰度流程至少完整演练 1 次，阶段门禁明确且可复用。
2. 回滚演练成功，恢复时间满足 `phase5-slo.md` 定义阈值。
3. 上线后一周无 P0 事故，P1 问题均有 owner 与截止时间。

### 验证方式

1. 输出灰度执行记录（每阶段指标快照与决策结果）。
2. 执行至少 1 次演练回滚并核对恢复指标。
3. 召开上线后复盘会并固化行动项清单。

### 输出物

1. `docs/refactor/phase5-rollback.md`
2. `docs/refactor/phase5-go-live-report.md`

## 6. 风险与依赖

### 6.1 主要风险

1. 监控口径不统一：导致“可见但不可定位”。
2. 压测样本失真：测试结论无法代表生产。
3. 自愈策略过激：可能引发误恢复与资源震荡。
4. 灰度窗口不足：问题未暴露即扩大放量。

### 6.2 风险缓解

1. 指标字典评审 + 双人校对 SLI 计算口径。
2. 压测数据集与生产样本对齐，并设定最小覆盖标准。
3. 自愈策略默认灰度启用，保留 feature flag 快速关闭路径。
4. 严格执行 Go/No-Go 门禁，不满足阈值禁止进入下一阶段。

### 6.3 关键依赖

1. Phase 4 的 W2/W4 能力需完成并稳定（校验预算、watchdog 细化）。
2. 具备稳定测试环境、可重复数据集与压测资源。
3. 值班机制、告警接收人、升级路径已明确。
4. 产品/运维/研发共同确认 SLO 与回滚阈值。
